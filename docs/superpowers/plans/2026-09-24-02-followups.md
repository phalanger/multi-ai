# 02 计划遗留事项（供后续计划引用）

来源：02-probe 执行过程中各任务审查、最终审查与修复复审的裁决。
写 03-core、04-app 计划时必须逐条处理本文件。

## 验证记录

- **V1 已完成（2026-09-24）**：在 macOS（zellij 0.45.1，Rust 1.98）上
  全量 100 个测试通过（含两个 `#[cfg(unix)]` install 测试），clippy 无警告。
  同时发现并修复一个依赖宿主环境的测试：`/opt/homebrew/bin` 已装 zellij
  时查找顺序测试失败；已拆出 `find_zellij_in` 与 `default_dirs`。
- **V2 未能确认**：`ZELLIJ_SOCKET_DIR=<空目录>` 下 `list-sessions -n`
  仍列出缓存中可恢复的 session（`(EXITED - attach to resurrect)`，退出码 0），
  无法造出“零 session”。探针继续以输出文本 `No active zellij sessions`
  判断，不依赖退出码；可恢复的 session 被解析为 `exited: true`，不轮询其 pane。
- **待办：端到端部署验证**：需要在远程 Mac 与 Ubuntu 主机上，用 GitHub
  Actions `probes` 产物里的 `mai-probe` 实测部署流程（探测、上传、
  install-hooks）。remote 主机上不构建也不打包本程序；用户在远程主机上
  自行 checkout 代码并本地编译，仅用 `probes` 产物里的探针二进制做部署
  端的验证。

## 03-core 必须处理

- **C1 zellij 命令超时与报错节流**：`zellij action` 挂起会卡住整个
  serve 循环；同一 session/pane 的持续错误每个周期重复上报。
  为子进程加超时，并按（错误码，session/pane）每次故障只报一次。**（已在
  03b 处理）**
- **C2 spool 定期清理**：目前只在 serve 启动时清理超过 7 天的文件；
  长时间运行的 serve 应每天清理一次。**（已在 03b 处理）**
- **C3 hook 与 serve 的数据目录一致**：hook 在 agent 的交互环境中运行，
  serve 在 SSH exec 环境中运行；只有一方设置 `MAI_HOME` 时，
  事件会写到 serve 读不到的地方。考虑把数据目录写进 hook 命令。**（已在
  03b 处理）**
- **C4 serve 单实例**：半开的 SSH 连接可能留下旧 serve；
  Windows 上还会锁住 `mai-probe.exe` 导致无法重新部署。
  需要单实例保护；`ack.tmp`、`<config>.mai-tmp` 固定文件名也在此处理。**（已在
  03b 处理）**
- **C6 UTC 零点跨天**：记录按自身 `ts_ms` 归档到天文件，
  跨零点的极小时间窗口内可能被跳过；读取时可回看前一天文件的尾部。**（已在
  03b 处理）**
- **C7 Windows 本机启动探针的控制台窗口**：用 `CREATE_NO_WINDOW`。**（已在
  03b 处理）**
- **C8 构建哈希（已在 03a 处理）**：改为 SHA-256 比较，不需要构建哈希。

## 03e 必须处理

- **B1 Windows sshd 服务会话**：经 sshd 启动的探针运行在服务会话中，
  能否看到用户桌面会话里的 zellij session 未验证；本机 03a 测试中
  `zellij_path` 为 null（zellij 不在 PATH）。
  **（03d 未能验证：本机 sshd 的公钥登录尚未配置；配置后与 B20
  一起验证，不写钥匙串。另需在 Windows sshd 上实测 SFTP 改名正在运行的
  exe（Win32-OpenSSH 的 sftp-server 以 link+unlink 实现 rename，可能因
  exe 被锁而失败））**
- **B2 ssh-agent 认证未实测**：Windows 本机 agent 服务被禁用，Unix agent
  未在真实环境测试；需在启用 agent 的机器上手工验证。
- **B3 应用层 known_hosts 与钥匙串**：`ConnectOptions.learn_to` 指向应用自己的
  known_hosts；`KeyringStore` 首次真实使用时手工验证。
  **（03d：钥匙串写入或删除失败会作为提示上报；测试不写真实钥匙串，
  `KeyringStore` 的首次真实使用留到 04 手工验证）**
- **B4 ssh2-config 忽略 `Match` 块**：`Match` 下的指令会被默默地
  归到前一个 `Host` 上。
  **（已在 03d 处理）**
  （Include 的文件中的 Match 块无法识别，只给出提示）
- **B5 口令钥匙串键按原样使用私钥路径**：同一私钥的不同写法会被当成
  不同的键，重复弹窗要求输入口令。
  **（已在 03d 处理）**
- **B6 known_hosts 的 `@revoked` / `@cert-authority` 标记未生效**：
  russh 不解释这两种标记，一律按未知主机处理。
  **（已在 03d 处理）**
- **B7 SSH 认证阶段无应答超时**：keyboard-interactive 的轮次也不限次数；
  若 prompter 一直不应答会阻塞 connect（设计如此，需在应用中说明）。
  **（03d：keyboard-interactive 最多 10 轮；prompter 不应答时仍会
  一直等待，由应用的弹窗负责超时或取消）**
- **C5 install-hooks 只在单次部署内串行**：单次 `deploy` 调用中，同一主机的
  install-hooks 按顺序执行；但没有任何机制阻止对同一主机并发发起多次
  connect/deploy（例如用户重复点击部署）。03b 主机管理器必须按主机把
  connect 与 deploy 串行化。**（已在 03b 处理：每主机一个任务串行连接与部署；
  `SystemConnector::gate` 供 03c 终端连接共用）**
- **B8 自实现的 known_hosts 容错解析**：目前直接调用 russh 的
  `check_known_hosts_path`，遇到无法解析的行（如非 UTF-8）整份文件判为
  `Unreadable` 并拒绝连接。需要自己实现一个容错解析器：整份内容按有损
  方式解码，逐行跳过解析失败的行而不是整份拒绝，并支持哈希主机名
  （`|1|salt|hash`，HMAC-SHA1）。在自实现解析器完成之前，无法解析的文件
  维持现状——拒绝而不是跳过。
  **（已在 03d 处理）**
- **B9 load_key 在服务器接受公钥前就解密每个身份文件**：`authenticate`
  遍历 `identity_files` 时对每个文件调用 `load_key`，加密的私钥会先向用户
  要口令（并可能提示记住），即使服务器最终不会用这把公钥登录。应改为
  先用公钥（无需解密私钥）探测服务器是否接受，再解密匹配的那一个。
  另外，一个从文件里试过的私钥，如果同一把钥匙也在 ssh-agent 里，
  `try_agent` 还会再试一次，白白消耗服务器的 `MaxAuthTries`。
  **（已在 03d 处理）**
- **B10 已知主机确认与上传窗口的并发问题**：两个并发的 connect 同时遇到
  同一个未知主机，会各自弹一次确认框，并且都各自 `learn`，known_hosts
  里出现重复行；两个并发的 deploy 会共享同一个 `<exe>.upload` 临时文件、
  互相覆盖。03b 主机管理器必须按主机把这些操作串行化（与 C5 相同的机制）。
  **（03b 部分处理：同一应用内已串行；两个应用同时连接同一未知主机
  仍会各自确认）**
  **（03d：`learn` 不再写重复行）**
- **B11 POSIX 探测信任全部 stdout**：`detect` 把 `uname -sm` 与
  `printf '%s' "$HOME"` 的整段 stdout 当作有效输出解析；登录 shell 的
  rc 文件如果多打印了东西，会污染 `$HOME`/`uname` 的解析结果。应该把
  探测输出包在哨兵标记之间，只解析标记之间的内容。
  **（已在 03d 处理）**
- **B12 cmd 下未定义的 `%USERPROFILE%` 按字面量回显**：`detect` 对 cmd 会话
  执行 `echo %USERPROFILE%`；如果该变量未定义，cmd 会原样输出
  `%USERPROFILE%` 而不是报错，`home` 会被设成这个字面量。
  **（已在 03d 处理）**
- **B13 ProxyJump 路径缺少集成测试与真实环境测试**：`connect` 里的多跳
  逻辑目前只有单跳的进程内测试覆盖，没有经跳板机的集成测试，也未在
  真实网络环境验证过。
  **（03d：已加经跳板机的进程内集成测试；真实网络仍未验证）**
- **B14 config.rs 递归解析嵌套 ProxyJump，但 connect 从不使用**：
  `resolve` 会递归解析跳板主机自己的 `ProxyJump`（受 `MAX_JUMP_DEPTH`
  限制），但 `client::connect` 的注释明确说“跳板主机自己的 ProxyJump
  设置不会被跟随”，两处行为不一致，需要决定保留哪一个语义。
  **（已在 03d 处理）**
- **B15 需要在真实的双因素主机上人工验证**（与 B2 一起处理）：
  keyboard-interactive 的 2FA 流程只在进程内测试服务器上验证过；
  russh 0.63 的进程内测试服务器不会发送 `partial_success = true`，
  真实的部分成功场景需要人工验证。
- **B16 agent_auth 忽略 partial success，且 keychain 写入失败不上报**：
  `agent_auth` 只在 `r.success()` 时返回成功，一旦服务器要求 2FA 之类的
  partial success，会被当成失败继续遍历其余 agent 身份，排在前面、
  原本应该重试的方法不会被重试；`SecretStore::set`/`delete` 调用失败时
  用 `let _ =` 静默丢弃错误，用户不会知道口令/密码没有被记住或清除。
  **（已在 03d 处理）**
- **B17 检测 kex 阶段的测试缺口（低优先级）**：`slow_host_key_answer_does_not_time_out`
  与 `timed_out_connection_never_prompts_later` 覆盖了主机密钥确认阶段的
  超时窗口，但握手中检测到密钥交换本身（尚未进入 `check_server_key`）的
  窗口没有专门测试。
- **B18 上传时删除与重命名之间的窗口，以及未实现的校验/回退**：
  `upload` 在删除旧文件与 `rename` 到位之间存在窗口；如果此时有一个正在
  运行的 Windows 探针进程锁住了旧文件，删除会失败（与 C4 相关）。
  另外，设计文档 4.2 提到的“上传后校验”和“SFTP 不可用时回退 exec 写入”
  均尚未实现。**（03b 部分处理：替换前先 `stop` 本 client 的 serve；
  另一个 client 的 serve 仍会锁住 Windows 上的文件）**
  **（03d：上传后在主机上校验 SHA-256，旧文件改名挪开再替换；
  SFTP 不可用时回退 exec 写入仍未实现）**
- **B19 上传时 Windows exe 锁的范围比 B18 更广**：除了另一个 client 的
  serve，一个短命的 `mai-probe hook` 进程也会短暂锁住 exe。这会导致
  `Problem::Deploy`（等待用户处理）而不是自动重试。建议在把新文件移动
  到位之前，先把旧文件改名挪开（例如加 `.old` 后缀），而不是直接删除。
  **（已在 03d 处理）**
  （远程 Windows sshd 上的 SFTP 改名见 B1，尚未验证）
- **B20 cmd 引号（M1）**：在 cmd 登录 shell 下，
  `"<probe>" serve ... --zellij "<path>"` 里有 4 个引号字符；如果
  Win32-OpenSSH 用 `cmd /c` 执行，去引号的过程可能会破坏它。另外，
  `quote_arg` 在 cmd 下不会转义 `"` 或 `%`。需要和 B1 一起验证，包括跑一次
  `serve --zellij <path>`。
- **B21 本地/远程探针的 stderr 被丢弃**：启动失败（规则文件错误、pid
  文件 IO 错误）只表现为“probe stream closed”，然后无限重试。应保留一段
  简短的 stderr 尾部，作为 Retrying 的原因。**（已在 03c 处理）**
- **B22 服务器拒绝 SSH 环境变量请求时没有回退**：没有实现设计 7 里的
  `LANG=... LC_CTYPE=...` 命令前缀回退；应结合终端连接一起实现。**（已在
  03c 处理）**
- **B23 同一 client 在同一时刻被启动两次 serve**：两者都会继续运行
  （竞态）。在同一个应用内，按主机的任务能防止这种情况。
- **B24 设计 2.2 的 `Transport` trait 未实现**：03b 使用的是
  `host::Connector`。03c 应该要么采用 `Connector` 加一个终端对应物并
  更新设计 2.2，要么实现 `Transport`。**（已在 03c 处理）**
- **B25 首次 attach 偶发无输出**：03c 验证时，Mac 上第一次经应用 attach
  新 session，zellij 20 秒内没有任何输出（PTY 仍在回显输入，说明 zellij
  未进入界面），之后连续 3 次都正常，未能复现。需要在更多主机上观察；
  若再现，记录 SSH exec 的 shell 与启动文件行为。假设：安装、升级或清除缓存
  后的首次启动，zellij 要编译 WASM 插件，可能无输出地持续 10 到 30 秒。
  下次先查看 `~/Library/Caches/org.Zellij-Contributors.Zellij`，或为手动执行的
  `zellij attach --create` 计时。
- **B26 SSH PTY 建立过程**（03c 最终审查）：
  - env 或 exec 的应答超时（10 秒）时按被拒绝或被忽略处理；迟到的应答
    会被当成下一个请求的应答，应答从此错位。
  - 建立失败（pty 被拒、exec 被拒、通道关闭）时没有关闭通道，每次失败的
    打开都会在服务器端泄漏一个通道，直到连接断开。
  - `reply()` 还会丢弃应答之前到达的 Data；对 OpenSSH 无害，但值得记录。
- **B27 终端重连行为**（03c 最终审查）：
  - 单个 PTY 的输出结束且没有 Exit 时，整条终端连接都被当作丢失。
  - 重连成功后退避立即复位，没有像探针连接那样的 `STABLE_AFTER`；
    两者叠加可能每秒重连一次，每次都是一整轮 SSH 连接加认证。
  - 连接中断时 `open_terminal` 失败，调用方只得到笼统的“terminal connection
    is down”，看不到真正的原因（例如需要认证）；`Term` 状态事件里有原因。
- **B28 终端任务连接期间不处理该主机的命令**（03c 最终审查）：
  - 连接可能在等待主机密钥或口令确认，attach 最多可等 4 × 10 秒。
  - 期间 Close、Stop、Retry 全部排队。
  - 可考虑采用 `run_host` 里的 `busy()` 模式。
- **B29 remove_host 后以同一 id 再 add_host**（03c 最终审查）：
  - 旧任务（探针或终端）已入队的事件可能到达新主机，例如过期的
    `Term(Some(Retrying))`。
  - 时间窗口很小。
  - 每次 add 带一个代数标记即可解决。
- **B30 没有探针时的终端 zellij 路径**（03c 最终审查）：
  - 探针一直连不上时（设计 11：主机降级为只有终端），远程 attach 使用
    PATH 里的 `zellij`。
  - macOS 上非交互 SSH 的 PATH 不含 `/opt/homebrew/bin`，终端会立刻以
    `Exited(Some(127))` 结束。
  - 应回退到登录 shell 或常见安装位置。
- **B31 以 `-` 开头的 session 名**（03c 最终审查）：会被 zellij 当成选项，
  目前没有任何转义。
- **B32 本机终端的 locale**（03c 最终审查）：
  - `local_env()` 在非 Windows 系统上总是把 LANG/LC_CTYPE 设为
    en_US.UTF-8，会覆盖用户自己的设置（如 zh_CN.UTF-8）。
  - 在没有 en_US.UTF-8 的精简 Linux 上，它会退回 C locale。
  - 只应在环境里完全没有 UTF-8 locale 时才补上。
- **B33 关闭终端应保留 session**（03c 最终审查）：
  - 2026-10-05 已在本机 Windows 验证：`attach --create` 一个临时 session，
    不按 Ctrl+q 直接关闭终端，session 仍在列表中。
  - Mac（远程 SSH）尚未验证；下次 Mac 主机在线时验证。
- **B34 SFTP 上传超时**：在慢链路上传约 4.8 MB 的探针时，russh-sftp 请求
  超时，被归为 `Problem::Deploy`（需要用户处理）；按设计 3.4 应作为网络类
  错误自动重试，或加长 SFTP 超时 / 分块写入。03d 验证时 Ubuntu 首次上传出现
  过一次，重试成功。
- **B35 跳板主机自身的 ProxyJump 被忽略时没有提示**：设计 3.1 不跟随，
  嵌套跳板的用户只看到不断重试；应给出 notes 提示。
- **B36 known_hosts 同一主机有多条同类型密钥**（密钥轮换、通配行加具体主机行）
  时按设计 3.3 视为“不一致”，比 OpenSSH 严格；需决定是否放宽为
  “同一文件内有匹配即可”。
- **B37 连接失败时 notes 不显示**：部署失败等（认证失败除外）时 notes
  不会显示；需要在 `OpenError` 上携带。
- **B38 测试会连到真实的 ssh-agent**：`refused_passphrase_moves_on_to_password`
  等测试在密钥失败后会连到真实的 ssh-agent / Pageant（若存在），违背测试不接触
  真实环境的约束；agent 连接应可注入。
- **B39 口令钥匙串键改为规范化路径的升级影响**：升级前记住的口令会再询问
  一次，旧条目残留在钥匙串中。
- **B40 `authenticate_publickey_with` 的错误文本**：失败时错误文本用 Debug
  格式（该错误类型无 Display）。

## 04-app 必须处理（或在 03 顺带处理）

- **S1 hook `Exited` 后被抓屏重新绑定**：agent 退出后，残留的
  标题（`Claude Code`）或最后一屏会让下一轮抓屏重新识别该 pane，
  随后产生一次虚假的 `Done` 提醒。建议：hook `Exited` 之后，
  至少出现一次“识别失败”才允许抓屏重新绑定。**（已在 03b 处理）**
- **S2 仅抓屏识别的 agent 短暂失配**：Claude 在默认权限模式或部分
  弹窗（如 AskUserQuestion、计划确认）下屏幕特征都不匹配时，
  会被报告为 `Exited` 再重新识别，期间的 `NeedsInput` 会丢失。
  建议：只要该 agent 自己的任一规则（标题、命令、屏幕、
  needs-input、done）仍匹配就保留绑定，或连续两次失配才判定退出。**（已在
  03b 处理）**
- **S3 `paste -p` 实测**：`SendText` 只核对了 `--help` 参数形式，
  在界面联调时实测。
- **S4 设计文档 4.5 措辞**：显式 `--zellij` 路径不存在时不再回退到
  PATH 或登录 shell，文档中的回退链需注明这一点。**（已在 03b 处理）**
- **S5 开发脚本（用户决定）**：在 `./scripts` 下新增六个脚本，
  Windows 与类 Unix 各一份：
  - `debug-desktop.sh` / `debug-desktop.ps1`：调试构建并启动桌面应用。
  - `release.sh` / `release.ps1`：发布构建。
  - `install-local.sh` / `install-local.ps1`：本地快速安装，供发布前
    验证使用。
  这些脚本及其用途需要写进用户可见的文档（例如 README 或开发者文档），
  与本文件的记录保持一致。
- **S6 应用重启后 agent 状态丢失**：hook 事件交给监控任务后即确认，spool 不再
  重放；应用重启后，只靠 hook 识别且正停在 `NeedsInput`/`Done` 的 agent 显示为
  未知，直到下一个事件。04 需持久化 `Tracker` 状态，或启动时回放最近的事件。
- **S7 zellij 查找的登录 shell 若启动常驻子进程**：`output_with_timeout` 在
  进程正常退出后等待管道关闭，若其子进程继承了 stdout 会一直等待；罕见，
  发生时改为超时后放弃读取。
- **S8 被强制结束的 serve 留下 pid 文件**：无害（下一个 serve 会核对进程），
  可在 04 的“清理”功能中一并删除。
- **S9 命令会重置静默计时器**：在 `host.rs` 里，serve 循环中每条命令都会
  重启 20 秒的静默计时器，而 `link.send` 没有超时。频繁的界面命令，或者
  一个发送窗口已满的半开通道，都可能因此推迟甚至阻塞检测。应该在整个
  循环中保持同一个静默截止时间，并给 `send` 加上超时。
- **S10 Update 接收端被关闭**：如果界面在 `HostManager` 仍存活期间丢弃了
  `Update` 接收端，监控任务会结束，但各主机任务仍在继续连接、确认 hook
  事件，而这些事件已经无人接收。`emit` 应该报告失败，任务应随之停止。
- **S11 被移除主机的 agent 仍留在 Tracker 里**：`Monitor::remove_host`
  没有清理该主机在 `Tracker` 里的 agent，所以 `pending()` 仍会列出它们，
  重新添加该主机时它们还会复活。需要新增 `Tracker::remove_host`。
- **S12 同一台机器的两条主机记录**：例如同一台 Mac 被加了两个名字，或者
  `local` 与 SSH 到同一台机器并存。它们共用同一个 client id 和数据目录，
  于是各自的 serve 会互相 stop 对方，两边都会反复抖动。需要检测重复目标，
  或者在文档中说明这个限制。
- **S13 首次连接时的提醒突发**：一次新的应用安装（新的
  `ack-<client>`，包括这次升级后的既有主机）会重放最多 7 天的 hook 事件，
  并对每一个历史的 NeedsInput/Done 都发出提醒。应该对明显早于本次连接
  时间的事件抑制提醒。
- **S14 ConPTY 的光标位置查询**：本机 Windows 终端启动时 ConPTY 发出 `ESC[6n`
  并等待答复。xterm.js 默认会应答；04 需实测，且应用不得再代为应答。
- **S15 终端输出量大**：attach 新 session 的前几秒可有数百 KB 输出（zellij 重绘、
  提示弹窗）。经 Tauri event 转发时需合并批次或限速，避免界面卡顿。
  另外，`ssh::pty` 在 `select!` 里 await `write.data`，大段粘贴会卡住输出的读取。
- **S16 无界通道**：输出量大而界面跟不上时，内存会无限增长。
- **S17 终端连接没有 `Connecting` 状态**：连接过程中界面无法显示
  “正在连接终端”。
- **S18 连接提示（notes）的清除**：`HostEvent::Notes` 只在有提示时发出；
  重连后没有提示时不发事件，UI 需在该主机重新连接（`Probe(Connecting)`）
  时清除旧提示，否则会一直显示过期内容。
